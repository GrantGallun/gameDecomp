# Controller and storage audit — September 11, 2026

Read-only audit of the running frozen runtime. No campaign state, model configuration, code, private DB or service was changed. Measurements are small warm-cache observations during the live workload, not controlled end-to-end benchmarks.

## Strongest opportunities

1. **Copy only missing attempt-run payloads during worker synchronization.** `eval/campaign_workers.py:55-56` removes private-only run records then executes `INSERT OR IGNORE INTO attempt_runs SELECT * FROM upstream.attempt_runs` on every dispatch. The authoritative DB is on `/mnt/c`; the workers are native WSL. A read of all 5,025 run rows transferred 19,359,433 bytes and took **1.283 s**. Reading just the 5,012 IDs in an earlier observation took **0.0023 s** through the primary-key covering index. Fetch the upstream/local ID sets, retain existing orphan cleanup, and fetch complete rows only for missing IDs, in bounded chunks. This retains even unattached historical run records and avoids relying on rowid monotonicity or new watermarks. Alternatively use an explicitly plan-verified indexed anti-join that fetches full row payload only after the missing-ID predicate. The current statement's exact write-side time is uninstrumented, so the measured read cost is evidence of opportunity, not a proven saved duration.

   Validation: isolated databases with complete historical row/config equality; runs attached only to proposals; runs with no attempts; private generated runs cleaned up after import; legacy missing cutoff marker; collision behavior; repeated synchronization; interrupted import replay. Time the actual synchronize call before/after on identical private copies. Preserve attempts/proposals/edge ID mappings and import transaction semantics.

2. **Optimize full input hashing without trusting timestamps.** `eval/fast_campaign.py:191,241` performs full verification once per dispatch and once per import. `eval/frozen_wavefront.py:40` does `Path.is_file()` followed by another `Path(...).read_bytes()`, adding redundant metadata work. Exact production verification measured **1.636 s/pass**; read-bytes plus SHA-256 without the extra `is_file` measured **1.100 s/pass**. One open, descriptor-based regular-file validation, and hashing all bytes could reduce overhead while retaining all content checks. Handle missing files, unreadable files and directory replacements as frozen-input errors. A descriptor pre/post metadata check can detect changes during a read, but must never replace actual content hashing. Benchmark this small option first.

   Across 16,095 pins, there are 13,012 workspace/target files (41.42 MB, approximately 2,003 functions), 2,281 original assembly files (16.86 MB), 365 frozen code files (4.50 MB), 170 project headers (0.85 MB), 227 original C/header files (3.42 MB), and 40 toolchain/build/ROM inputs (21.11 MB). Most files hashed for each tiny job belong to other functions. A larger optimization would use a verifiably immutable input snapshot or explicitly amended per-job dependency closure. Simply dropping unrelated pins, hashing periodically, checking only mtimes/sizes, or accepting an unverified background scan weakens the current whole-regime integrity contract. Do not make those changes implicitly.

   Validation: altered content with restored mtime/size; missing files; directory replacement; changed symlink target; existing full-pin mismatch behavior; exact same accepted hash map; bounded warm/cold replay with unchanged candidate and verdict.

3. **Reduce fresh-process overhead after fixing runtime wrapper lifetime.** `eval/fast_campaign.py:181-182` uses spawn and `max_tasks_per_child=1`; importing the frozen `eval.fast_campaign` in one fresh WSL Python process measured **0.550 s**, peak RSS about 55 MB before executing a job. This is material for 2.6–4.9 s local rewrite jobs. `fast_runtime.install` and `_worker` currently monkeypatch globals, including SQLite connection authorization, so changing the process recycling count alone is unsafe. Wrappers must install once or be uninstalled in `finally`, with per-job metrics, DB authorization, model lock, pin binding and cache roots updated correctly. Slot-sticky workers could also improve cache locality, but must not retain stale source/evidence state.

   Validation: two jobs sequentially in one process, different slots/DBs/functions/pins; no stacked calls/counters; authorizer bound to the second DB; stale cache invalidation; worker exception followed by valid job; bounded RSS growth; same cold/warm outputs and verdicts. Keep private slot ownership until durable import and checkpoint.

4. **Move only measured Windows I/O hot paths to native WSL, using explicit authoritative-state migration.** The main DB is 1,465,249,792 bytes, `journal_mode=delete`; private DBs already live in native WSL. The metadata read above gives concrete evidence of crossing-filesystem overhead, but does not justify blindly moving the 1.46 GB authoritative DB. A safe migration requires a paused durable boundary, backup/hash validation, config amendment, one authoritative DB, complete import ledger preservation, and a Windows-readable dashboard/export mirror. Copying a live SQLite file without backup coordination or allowing two writable DB authorities is unsafe. Frozen code relocation also changes pinned paths and cache identity. The smaller missing-run-row fix should be measured before either migration.

## Timing evidence and blind spots

- Recent immutable commits 337 through 371 covered 17 completions over **164.32 s**. Recorded dispatch/controller time rose **53.92 s**; typical refill records take **2.9–3.1 s**, with a 5.2 s outlier. This agrees with full hashing plus the repeated run-table payload read, but does not isolate their write-side durations.
- Twenty recent canonical receipts showed raw-result-to-canonical-receipt delay usually **1.75–1.86 s**, with peaks **3.8, 4.26, and 7.15 s**. Several local rewrite jobs themselves take only **2.6–4.9 s**. Serial import/refill costs are therefore material for the CPU lane and can delay GPU preparation. File timestamps approximate completion lag; they are not precise internal stage instrumentation.
- `controller_seconds` at `fast_campaign.py:190-221` times dispatch only. It omits import-side full hash verification, receipt reads, validation, merge, remapping, canonical write and accept (`:241-252`). Add separate hash/sync/isolate/spawn/import/accept timing and raw-ready-to-dispatch delay. Otherwise the dashboard understates controller work.
- `worker.wall_seconds` starts at `:51`, after runtime installation/imports; it excludes spawn/import/wrapper setup. Include submitted/start/end timestamps to expose this gap.
- `session_seconds` is recorded only after the entire batch drains (`:271`). It stayed **3974.9633** while completed count rose from 184 to 201 during this audit, so improvements/hour displayed in the UI is stale during a batch. Preserve a persisted accumulated total plus live elapsed time, avoiding double counting on resume.
- The service runs batches of **50** despite launch.json storing 1000; `campaign_service.py:60` overrides the command. Each batch drains remaining jobs, exits and reloads the large checkpoint. The supervisor polls process completion in 10-second sleeps (`:161-165`), adding 0–10 seconds at restart. Larger/continuous controller sessions and event-aware heartbeat waits can reduce this, but this is less urgent than per-job costs. Keep pause signals effective and budgets explicit.
- Queue projection (`fast_campaign.py:84`, `repair_queue.py:158`) currently takes approximately **0.04–0.05 s/completion**, and incremental checkpoints approximately **0.15–0.28 s/save**. They are lower priorities. `dispatch_items` recomputes profiles for all eligible nodes, but present measurements do not justify redesigning it before eliminating the larger costs.
- Attempts, parent/run function references and attempt-edge child IDs already have indexes. The edge delta query uses the covering `ae_child` index. Adding generic indexes or declaring SQLite itself the bottleneck is not supported.

## Correctness constraints

Do not refill a private slot before its prior result is transactionally imported and durably represented in the checkpoint. Preserve raw receipts and exactly-once import ledger replay. Worker snapshot history must remain complete; filtering to current-function attempts changes available knowledge. Out-of-order completion must retain source/evidence checks and full input contract. Keep candidate compilation, frontend, semantic and exactness gates unchanged; these optimizations concern orchestration only.

Recommended immediate order: precise timing, missing-run payload copy, single-open full hashing, then isolated process-reuse experiment. Reassess GPU feed and accepted improvements/hour after those changes; no whole-game speedup is claimed from this audit.
