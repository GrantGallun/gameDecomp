## Execution and interpretation

`run_frontier.py --run` runs the ordinary frozen controller with the existing
three-worker configuration on four WSL CPUs. It uses a 15-job first batch, then
200-job batches, unchanged per-function budgets, and fresh receipts. The initial
pass is deterministic: model generation, runtime capture and ROM integration
remain disabled. It stops on exhausted deterministic work, a requested pause,
newly parked nodes, controller failure, invariant failure, or the explicit
1000-batch ceiling. A ceiling must be reported as a ceiling, not convergence.

`frontier/progress.json` records completed batches, jobs, attempts and exact
gains. `frontier/final.json` is produced after a clean stop. A `STOP` file under
`frontier/` stops between batches; the native service pause stops dispatch at a
work boundary. `diagnose.py` reads current checkpoint evidence and distinguishes
in-flight receipts, remaining deterministic routes, model-selected routes,
compiler/frontend failures, semantic limitations and byte residuals. Checkpoint
in-flight metadata alone is not proof that worker processes are alive.
